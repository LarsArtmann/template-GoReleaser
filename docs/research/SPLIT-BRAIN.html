Split-Brain Issues in the Data Model

A point-in-time audit of GoReleaser-Wizard's domain layer for duplicated types, divergent defaults, and parallel sources of truth. Ten split-brain sites were identified across the domain, application, and infrastructure layers — three critical enough to silently produce different configurations from identical inputs.

00Summary

The codebase claims a single source of truth through SafeProjectConfig, but in practice the same concepts are defined two or three times in different packages with subtly different shapes. The most dangerous split is between NewSafeProjectConfig() (which sets FeatureLevelBasic) and ApplyDefaults() (which defaults to FeatureLevelStandard when the field is empty). A config built via the constructor and a config hydrated from YAML then defaulted end up with different feature levels, signing levels, and Docker support — silently.

Validation is similarly split: SafeProjectConfig.Validate() and ValidationUseCase.ValidateConfiguration() both validate the same struct but use different error codes, different rules (one requires non-empty action triggers, the other does not), and only one of them performs security checks. JobStatus is defined twice in the same build with different underlying kinds (int vs string) and different enum members.

The bottom line Three critical sites can produce silently divergent behavior from identical inputs. The other seven create maintenance traps that will drift further with each change. Consolidating each duplicated concept behind one canonical type — and treating SafeProjectConfig as the only constructable shape — eliminates the entire class.

♦Scope & Method

Every non-test .go file under internal/domain, internal/types, internal/config, internal/git, internal/utils, and cmd/goreleaser-wizard was inspected for the following split-brain patterns:

Duplicate type definitions

Same concept, two structs with different shapes or field names.

Multiple sources of truth

Constants, defaults, or validation rules defined in >1 location.

Bypassable smart constructors

"Safe" types that can be built invalid through a sibling type.

Drift-prone parallel logic

Functions that compute the same answer by independent code paths.

Severity is assigned by the combination of likelihood of divergence and blast radius if it diverges. A "critical" finding can already produce incorrect behavior today; an "important" finding will drift on the next change to either copy; a "minor" finding is noise but worth noting.

◆What's already excellent

Before listing problems: the project does several things right that make the split-brain issues fixable rather than structural.

+
Typed enumerations with IsValid() Every enum (ProjectType, Platform, SigningLevel, etc.) is a named type with an IsValid() method. This is the right foundation; the splits are in the consumers, not the enums themselves.
+
Architecture enforcement via go-arch-lint .go-arch-lint.yml already forbids the domain layer from importing application or infrastructure. The structural boundary exists; only the type boundary inside it is leaking.
+
Centralized typed errors internal/domain/errors.go defines DomainError with Code, Message, Details, and recovery suggestions. The plumbing for structured errors is in place even where the error codes drift (see finding 7).
+
Small, focused files under 300 lines The workflow package was already split into workflow_core.go, workflow_execution.go, etc. This discipline makes consolidation mechanical rather than surgical.

01Findings

Ten split-brain sites, ordered by severity then impact.

Critical · Silent wrong output

Triple-duplicated GetGitHubOwner / GetGitHubRepo

internal/git/commands.go:290 · internal/utils/recommendations.go:101 · cmd/goreleaser-wizard/types/template_data.go:236-260

Three independent implementations of the same function with different behavior. A shells out through NewCommand(ctx).GetRepositoryInfo(). B delegates to A and falls back to the literal "owner". C uses a completely different exec.CommandContext("git", "remote", "get-url", "origin") path with its own parser (parseGitHubRemote). All three can return different answers for the same repository. 

// A — internal/git/commands.go:290
func GetGitHubOwner() string {
    info, err := NewCommand(ctx).GetRepositoryInfo()
    if err != nil { return "owner" }
    return info.Owner
}

// B — internal/utils/recommendations.go:101 (wraps A)
func GetGitHubOwner() string {
    if owner := git.GetGitHubOwner(); owner != "owner" {
        return owner
    }
    return "owner"
}

// C — cmd/goreleaser-wizard/types/template_data.go:253
func GetGitHubOwner() string {
    owner, _ := parseGitHubRemote()  // different impl entirely
    return owner
}
Fix Keep one canonical implementation in internal/git. Delete B and C; have template_data.go import git.GetGitHubOwner(). The sentinel "owner" should be a named constant in one place, not three.
Critical · Silent config divergence

Two sources of truth for defaults: NewSafeProjectConfig vs ApplyDefaults

internal/domain/config_core.go:50-68 · internal/domain/config_defaults.go:10-131

The constructor hard-codes FeatureLevelBasic; the defaults method falls back to FeatureLevelStandard when the field is empty. A config created via NewSafeProjectConfig() already has a non-empty FeatureLevel, so ApplyDefaults() will not touch it. But a config hydrated from YAML with an omitted feature_level will receive FeatureLevelStandard. Two code paths, two outcomes, no enforcement.

The same pattern repeats across SigningLevel, DockerSupport, and ActionLevel: the constructor sets fixed values; ApplyDefaults derives them from ProjectType / FeatureLevel. They agree today for the CLI case but disagree for several other project types.

NewSafeProjectConfig (config_core.go:50)
ApplyDefaults (config_defaults.go:10)
ProjectType:    GetRecommendedProjectType()
FeatureLevel:   FeatureLevelBasic
SigningLevel:   SigningLevelNone
DockerSupport:  ""  // left empty
ActionLevel:    ActionLevelBasic
if FeatureLevel == "" {
    FeatureLevel = FeatureLevelStandard
}
// then derives signing/docker from FeatureLevel
SigningLevel   = FeatureLevel.GetRecommendedSigningLevel()
DockerSupport  = FeatureLevel.GetRecommendedDockerSupport()
Fix Make ApplyDefaults() the only place defaults are computed. The constructor should set nothing but the State field (or call ApplyDefaults() itself after setting ProjectType to the recommended value). This guarantees one code path regardless of how the struct was allocated.
Critical · Different validation outcomes

Dual validation: Validate() vs ValidateConfiguration()

internal/domain/config_core.go:71-213 · internal/domain/validation.go:38-71

Two methods validate the same SafeProjectConfig with different rules and different error codes. SafeProjectConfig.Validate() returns an error; ValidationUseCase.ValidateConfiguration() returns a *ValidationResult with a pipeline of validateBasicFields, validateTypes, validatePlatformArchCompatibility, validateBusinessRules, and validateSecurity. They disagree on:

  • Error codes: Validate() uses ErrInvalidProjectName for enum errors (line 96-102); the use case uses the correct per-field codes like ErrInvalidPlatform.
  • Action triggers: Validate() only checks that each existing trigger is valid; the use case requires at least one trigger (ValidateActionTriggers errors on empty).
  • Side effects: Validate() calls exec.LookPath for signing tools — a filesystem side effect inside what should be pure domain logic.
  • Security: only the use case runs validateSecurity.
Fix Validate() should be a thin delegate to ValidationUseCase.ValidateConfiguration() (or the reverse). One pipeline, one set of error codes, one place that decides whether empty triggers are valid. exec.LookPath belongs in an infrastructure check, not in domain validation.
Important · Compile-time ambiguity

Duplicate JobStatus with different underlying kinds

cmd/goreleaser-wizard/job_manager.go:31-40 (int) · cmd/goreleaser-wizard/types/template_data.go:89-97 (string)

JobStatus is defined twice in the same main package build: once as type JobStatus int with an iota block including JobStatusRolledBack and no JobStatusCancelled, and once as type JobStatus string with string constants including JobStatusCancelled and no JobStatusRolledBack. Whichever definition is in scope at a given file depends on import order; they are not assignment-compatible. 

// job_manager.go:32 — int-based
type JobStatus int
const (
    JobStatusPending   JobStatus = iota
    JobStatusRunning
    JobStatusCompleted
    JobStatusFailed
    JobStatusRolledBack   // only here
)

// template_data.go:89 — string-based
type JobStatus string
const (
    JobStatusPending   JobStatus = "pending"
    JobStatusRunning   JobStatus = "running"
    JobStatusCompleted JobStatus = "completed"
    JobStatusFailed    JobStatus = "failed"
    JobStatusCancelled JobStatus = "cancelled"  // only here
)
Fix Keep one definition. Prefer the string-based version (serializes cleanly for templates and JSON) and add JobStatusRolledBack to it. Delete the int version entirely.
Important · Same name, different shape

Duplicate ValidationResult type in two packages

internal/domain/interfaces.go:259-264 · internal/types/validation.go:13-18

Both packages define ValidationResult with the same JSON shape (is_valid, errors, warnings) but completely different element types. The domain version uses *DomainError for both errors and warnings and adds a Rules *ValidationRules field. The types version uses *ValidationError and *ValidationWarning and adds a Summary ValidationSummary field. Consumers must remember which package they imported, and the two cannot be substituted.

domain.ValidationResult
types.ValidationResult
type ValidationResult struct {
    IsValid  bool
    Errors   []*DomainError
    Warnings []*DomainError
    Rules    *ValidationRules
}
type ValidationResult struct {
    IsValid  bool
    Errors   []*ValidationError
    Warnings []*ValidationWarning
    Summary  ValidationSummary
}
Fix Keep the domain version as canonical. The types package should either import it or be deleted entirely. If separate DTO and domain shapes are truly needed, rename one (e.g. ValidationResultDTO) so the collision cannot happen silently.
Important · Subset interface drift

Duplicate Logger interface — generators define a strict subset

internal/domain/interfaces.go:151-168 · cmd/goreleaser-wizard/generators/goreleaser.go:23-28

The domain Logger interface has 12 methods (Debug/Info/Warn/Error plus their *Context variants, plus WithField, WithFields, WithError). The generators redefine a 4-method subset. Any struct satisfying the generators' interface does not satisfy the domain one. The two can drift independently — adding a method to one does not propagate.

Fix Delete the generators' Logger and import the domain one. If the generators genuinely only need four methods, define a small GeneratorLogger interface in the generators package and have the domain logger satisfy it — but do not name both Logger.
Important · Drift-prone parallel logic

Three parallel sets of recommendation functions

internal/domain/enums.go:232-310 · enums_project.go:87-152, 216-267

The same question — "what is the recommended signing level for this project?" — is answered by three independent code paths: standalone functions keyed on ProjectType, methods on ProjectType, and methods on FeatureLevel. NewSafeProjectConfig uses one path; ApplyDefaults uses another. They agree today for the common cases because someone manually kept them in sync, but there is no compile-time guarantee they stay aligned. 

// A — standalone (enums.go)
func GetRecommendedSigningLevel(pt ProjectType) SigningLevel

// B — method on ProjectType (enums_project.go)
func (pt ProjectType) RecommendedSigningLevel() SigningLevel

// C — method on FeatureLevel (enums_project.go)
func (fl FeatureLevel) GetRecommendedSigningLevel() SigningLevel
Fix Pick one owner per question. Signing recommendations belong to FeatureLevel (since feature level is the user-facing knob); platform and architecture recommendations belong to ProjectType. Delete the standalone functions and route every consumer through the method form.
Important · Identical enum, two types

WorkflowStatus duplicates JobStatus string values

cmd/goreleaser-wizard/types/template_data.go:89-97, 130-138

WorkflowStatus and the string variant of JobStatus have identical values (pending, running, completed, failed, cancelled) but are separate types. They model the same 5-state execution lifecycle. A job and a workflow both progress through the same states; defining them twice means a future addition (e.g. paused) must be made in two places.

Fix Collapse both into a single ExecutionStatus type in the domain layer. A workflow and a job both have an ExecutionStatus; the wrapper structs (WorkflowState, JobExecutionResult) already differentiate them.
Important · Same answer, two locations

Recommended platforms defined twice

internal/domain/enums_platform.go:195-200 · enums_project.go:103-124

GetRecommendedPlatforms() returns [Linux, Darwin] as a fixed list. ProjectType.RecommendedPlatforms() returns the same list via a switch whose every case (except Mobile) also yields [Linux, Darwin]. NewSafeProjectConfig uses the former; ApplyDefaults uses the latter. They agree today, but a future change to add PlatformWindows to the CLI case would silently diverge from the standalone function.

Fix Delete GetRecommendedPlatforms(). Every consumer should call spc.ProjectType.RecommendedPlatforms(). If a project-type-agnostic default is needed, expose it as ProjectType("").RecommendedPlatforms() or a named constant.
Minor · Noise, not a bug today

Eight identical error constructor functions

internal/domain/errors.go:174-245

NewValidationError, NewConfigurationError, NewBusinessRuleError, NewTemplateError, NewExternalServiceError, NewFileError, NewConfigError, and NewGitError all have the same signature (code ErrorCode, message, details string) *DomainError and the same body return &DomainError{Code: code, Message: message, Details: details}. They create the illusion of distinct error categories but encode no distinguishing information. (NewSystemError is the only one that differs — it takes an extra cause parameter.)

Fix Either (a) delete seven of the eight aliases and keep NewValidationError as the single constructor, or (b) if the intent is to tag error categories, add a Category field to DomainError and have each constructor set it. Today they are pure ceremony.

04Remediation

Ordered so each step is independently shippable and verifiable. Steps 1–3 close the critical silent-divergence gaps; steps 4–10 are mechanical consolidation.

1

Collapse defaults to ApplyDefaults

Make NewSafeProjectConfig set only State and then call ApplyDefaults. Add a table-driven test that constructs a config via the constructor and via YAML-hydration-plus-ApplyDefaults and asserts field equality. Files: config_core.go, config_defaults.go.

2

Unify validation behind ValidationUseCase

Replace SafeProjectConfig.Validate() body with a delegate call to ValidationUseCase.ValidateConfiguration. Move exec.LookPath out of the domain into an infrastructure checker. Audit error codes so every field uses its dedicated code (ErrInvalidPlatform, not ErrInvalidProjectName).

3

Delete duplicate GetGitHubOwner / GetGitHubRepo

Keep internal/git/commands.go as canonical. Remove the wrappers in internal/utils/recommendations.go and the parseGitHubRemote-based versions in types/template_data.go. Extract the "owner" sentinel to a named constant.

4

Collapse JobStatus / WorkflowStatus into one type

Introduce domain.ExecutionStatus (string-based, with all current members). Delete both cmd/.../job_manager.go's int version and types/template_data.go's two string versions. Update WorkflowState and JobExecutionResult to use it.

5

Consolidate ValidationResult, Logger, recommendation functions

Delete internal/types/validation.go's ValidationResult (or rename to DTO). Delete the generators' Logger. Delete standalone GetRecommended* functions whose logic already lives as methods on ProjectType / FeatureLevel.

6

Cleanup pass — error constructors and platform defaults

Collapse the eight identical error constructors to one (or add a Category field that actually distinguishes them). Delete GetRecommendedPlatforms() in favor of ProjectType.RecommendedPlatforms().
